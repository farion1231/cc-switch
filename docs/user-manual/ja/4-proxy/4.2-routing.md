# 4.2 アプリケーションルーティング

## 機能説明

アプリケーションルーティングとは、CC Switch に特定アプリの API リクエストをルーティングさせることです。各アプリには 3 つの接続モードがあり、アプリページ上部の「直接接続 / ルーティング / 集約」タブで確認できます：

| モード | 説明 |
|------|------|
| 直接接続 | クライアントがプロバイダーに直接接続します。切り替えで書き換わるのは設定ファイルの主要フィールドだけです |
| ルーティング | リクエストはまずこのマシンの CC Switch を経由してからプロバイダーに転送されます。フォーマット変換とフェイルオーバーが使えます |
| 集約 | Claude Code と Codex のみ。`/model` で選んだモデルに応じてリクエストを複数のプロバイダーに振り分けます。フェイルオーバーはしません。公式アカウントは既定のプロバイダーにしかできず、集約には加えられません |

このページでは「ルーティング」を説明します。ルーティングに入ると：
- アプリの API リクエストがローカルルーティング経由で転送される
- リクエストログと使用量の統計を記録できる
- フェイルオーバー機能を使用できる

## 前提条件

ルーティングには CC Switch が起動し続けている必要があります。ルーティングサービスを事前に起動しておく必要はなく、ルーティングに入るときに自動的に起動します。

ルーティングに対応するアプリ：Claude Code、Codex、Gemini CLI、Grok Build。

## ルーティングの開始

### 操作場所

アプリページ上部の「ルーティング」タブ。

### 操作手順

1. サイドバーでルーティングするアプリを選択
2. 上部の「ルーティング」タブをクリック（表示が切り替わるだけで、設定は変わりません）
3. 「ルーティングを開始」をクリックし、表示される確認ダイアログで「転送先」のプロバイダーを選んで、「ルーティングを開始」で確定

確認ダイアログには結果が書かれています。クライアント設定内のアドレスとキーを書き換えること（本物のキーは CC Switch に残り、ほかの設定は変わりません）、以後「ルーティング」タブでプロバイダーを変えても設定ファイルは書き換えないこと、CC Switch を起動したままにする必要があること（終了時に直接接続へ書き戻し、次回起動時に再接続します）が示されます。

複数のアプリを同時にルーティングに入れられます。「設定 → ローカルルーティング」の「ルーティングを使用中のアプリ」にそれらが一覧表示されます。

> ⚠️ 公式プロバイダー（Claude Official など）はローカルルーティング経由で転送できないため、ルーティングモードではこの種のプロバイダーに切り替えられません。カードには「公式サブスクリプションはルーティングを通りません。直接接続に戻すと使えます。」と表示されます。ただし Codex の OpenAI Official は例外です。

## ルーティングの仕組み

### 設定の変更

ルーティングに入ると、CC Switch はアプリの設定ファイルを変更し、API エンドポイントをローカルルーティングに向けます。

**Claude 設定の変更**：

```json
// ルーティング前
{
  "env": {
    "ANTHROPIC_BASE_URL": "https://api.anthropic.com"
  }
}

// ルーティング後
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://127.0.0.1:15721"
  }
}
```

**Codex 設定の変更**：

```toml
# ルーティング前
[model_providers.custom]
base_url = "https://api.example.com/v1"

# ルーティング後
[model_providers.custom]
base_url = "http://127.0.0.1:15721/v1"
```

**Gemini 設定の変更**：

```bash
# ルーティング前
GOOGLE_GEMINI_BASE_URL=https://generativelanguage.googleapis.com

# ルーティング後
GOOGLE_GEMINI_BASE_URL=http://127.0.0.1:15721
```

**Grok Build 設定の変更**：`~/.grok/config.toml` 内の、ルーティングで使うプロバイダーのモデルテーブルのリクエスト先アドレスが `http://127.0.0.1:15721/grokbuild/v1` に変わります。Grok Build の公式アカウントはローカルルーティング経由では使用できません。現在公式プロバイダーを使っている場合、ルーティングを開始するとエラーになるため、先にサードパーティのプロバイダーに切り替えてください。

ルーティング中、設定ファイル内の API Key はプレースホルダー `PROXY_MANAGED` に置き換えられ、実際の Key はローカルルーティングが転送時に付与します。プロバイダーの切り替えと同様に、ルーティングに入っても変更されるのはこれらの主要フィールドだけで、設定ファイル内のその他の内容は変更されません。

### リクエストの転送

ルーティングサービスがリクエストを受信すると：

1. リクエスト元を識別（Claude/Codex/Gemini/Grok Build）
2. そのアプリの現在のルーティング先を検索（フェイルオーバーが有効な場合はキューに従う）
3. 必要に応じてインターフェースフォーマットを変換し、プロバイダーの実際のエンドポイントにリクエストを転送
4. リクエストログを記録
5. アプリにレスポンスを返却

## ルーティング状態の表示

### アプリページの表示

ルーティングが有効になると：

- 「ルーティング」タブに有効マークが付き、タブの右側に「ルーティングが有効 → プロバイダー名」と表示されます（フェイルオーバー有効時は「キュー順」）
- ルーティング中のプロバイダーカードに「転送中」と表示されます
- ルーティングサービスが動いていない場合、アプリページに案内が表示され、「サービスを起動」と「直接接続に戻す」のボタンが現れます

### プロバイダーカードの状態

| 状態 | 説明 |
|------|------|
| 転送中 | ルーティングが実際に使用しているプロバイダー |
| 直接接続 | 直接接続のプロバイダー。ルーティングを抜けるとここに戻ります（マウスを重ねると「ルーティングを終了するとこのプロバイダーに戻ります」と表示） |
| ここへ転送 | ほかのプロバイダーにあるボタン。クリックするとルーティング先がそのプロバイダーに変わります |

## ルーティングの終了

### 操作手順

- アプリページで「直接接続に戻す」をクリックする（そのアプリだけが抜けます）
- または「設定 → ローカルルーティング」で「すべて直接接続に戻す」をクリックする（すべてのアプリが抜け、ルーティングサービスも停止します）。詳しくは [4.1 ローカルルーティングサービス](./4.1-service.md#ローカルルーティングの停止) を参照してください

### 設定の復元

ルーティングを抜けるとき、CC Switch は以下を実行します：

1. アプリの設定ファイルを直接接続のプロバイダー（ルーティングに入る前に使っていた、カードに「直接接続」と表示されているもの）に書き戻す。ルーティングに入るときのバックアップには依存しない
2. 現在のリクエストログを保存

CC Switch を終了するときも、まず設定ファイルを直接接続のプロバイダーに書き戻します。アプリのモードは変わらず、次回 CC Switch を起動したときにローカルルーティングへ再接続します。

## ルーティングとプロバイダーの切り替え

### ルーティングモードでのプロバイダー切り替え

ルーティングモードでプロバイダーを切り替える場合：

1. 「ルーティング」タブでプロバイダーカードの「ここへ転送」をクリック（フェイルオーバー有効時は、キューで調整します。[4.3 フェイルオーバー](./4.3-failover.md) を参照）
2. ルーティングサービスが新しいプロバイダーを使用してリクエストを即座に転送
3. **CLI ツールの再起動は不要**

これがルーティングモードの大きなメリットです：プロバイダーの切り替えが即座に反映されます。Codex、Gemini CLI、Grok Build を切り替えた後も画面には再起動の案内が表示されますが、ルーティング中で、切り替えによってモデルが変わらない限り、再起動しなくても構いません。

ルーティングモードで切り替わるのは、ルーティングが使うプロバイダーだけです。直接接続のプロバイダーはそのまま残り、カードに「直接接続」と表示され、ルーティングを抜けるとそのプロバイダーに戻ります。新しいプロバイダーが設定ファイルに書き込む内容（ローカルアドレス、モデル名など）が以前と同じであれば、切り替えても設定ファイルは変更されません。異なる場合（モデル名が違うなど）は、CC Switch が先に設定ファイルを更新します。このとき Codex、Gemini CLI、Grok Build は、新しいモデルを使うために再起動が必要です。

### 直接接続モードでの切り替え

直接接続モードでプロバイダーを切り替える場合：

1. 設定ファイルを変更
2. CLI ツールの再起動が必要

## 複数アプリのルーティング

複数のアプリを同時にルーティングでき、それぞれ独立して管理されます：

- 独立したプロバイダー設定
- 独立したフェイルオーバーキュー
- 独立したリクエスト統計

## 使用シーン

### シーン 1：使用量の監視

ルーティング + 「リクエストの使用量を記録」を有効にすると、ローカルルーティングを通過したリクエストを 1 件ずつ記録します。ルーティングを使っていない場合も、CC Switch は各ツールのローカルのセッションログから使用量を集計します。詳しくは [4.4 使用量統計](./4.4-usage.md) を参照してください。

### シーン 2：素早い切り替え

ルーティングを有効にすると、プロバイダーの切り替えに CLI ツールの再起動が不要になります。

### シーン 3：インターフェースフォーマットの変換

OpenAI や Gemini フォーマットのプロバイダーを Claude Code で使う場合や、Chat Completions / Anthropic Messages フォーマットのプロバイダーを Codex や Grok Build で使う場合は、いずれもルーティングに入る必要があります。

### シーン 4：フェイルオーバー

ルーティングに入ることは、フェイルオーバー機能を使うための前提条件です。

## 注意事項

### パフォーマンスへの影響

ルーティングにより少量のレイテンシ（通常 < 10ms）が追加されますが、ほとんどのシーンでは無視できます。

### ネットワーク要件

ルーティングモードでは、CLI ツールがローカルルーティングアドレスにアクセスできる必要があります。

### 設定のバックアップ

ルーティングに入るときはバックアップに依存しません。ルーティングを抜けるとき、CC Switch は直接接続のプロバイダーに基づいて設定ファイルを書き直します。また、CC Switch は各設定ファイルを初めて書き換える前に、元のファイルを `~/.cc-switch/backups/live-first-write/` にバックアップします。

## よくある質問

### ルーティング後にリクエストが失敗する

確認事項：
- ルーティングサービスが正常に実行されているか（設定 → ローカルルーティング）
- プロバイダーの設定が正しいか
- ネットワークが正常か

### 直接接続に戻っても設定が復元されない

考えられる原因：
- ルーティングの異常終了
- 設定ファイルが他のプログラムに変更された

解決方法：
- プロバイダーを手動で編集して保存し直す
- または再度ルーティングに入ってから抜ける
