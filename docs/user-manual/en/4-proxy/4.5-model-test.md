# 4.5 Connectivity Check

## Overview

The connectivity check quickly tells you whether a provider's address can be reached:

- CC Switch sends a lightweight request to the provider's request address (base URL); any HTTP response (including 401, 403, 404 and 5xx) counts as "reachable"
- Only network-level errors such as DNS resolution failure, connection refused, TLS errors or timeouts count as "unreachable"
- Latency is the time until the response headers arrive

> ⚠️ **The connectivity check does not send a real model request**, and it does not verify the API Key or model name. "Reachable" only means the address can be reached; it doesn't guarantee that auth or model settings are correct.

> 💡 Before v3.16.3, this feature was called "Model Test" (Stream Check) and sent a real streaming model request to the provider. Because many third-party gateways block such requests and cause false results, it has been replaced by the connectivity check, and you no longer need to configure a test model.

Non-official providers of every app can be checked, except MiniMax Code. Official providers (such as Claude Official and Claude Desktop Official) have no address to probe; on the cards of official providers and MiniMax Code providers, the check button is grayed out and can't be clicked.

## Run a Check

1. Hover over the provider card to show the action buttons
2. Click the **Connectivity check** button
3. Wait for the check to finish; the result appears as a toast message

| Result | Description |
|--------|-------------|
| reachable (xxx ms) | The address is reachable, and latency is within the "Slow-response threshold" |
| reachable but slow (xxx ms) | The address is reachable, but latency exceeds the "Slow-response threshold" |
| unreachable | Could not establish a connection (DNS / connect / TLS / timeout); check the request address and your network |

## Check Parameters

Settings → Advanced → Connectivity Check Settings

| Parameter | Description | Default | Range |
|-----------|-------------|---------|-------|
| Timeout (seconds) | Maximum wait time for a single probe | 8 | 2-60 |
| Max Retries | Retries only on timeout-type failures; connection refused, DNS failure and the like return immediately | 1 | 0-5 |
| Slow-response threshold (ms) | When the address is reachable but latency exceeds this value, it is marked as "slow" | 6000 | 1000-30000 |

## Relationship with Failover

The connectivity check does **not** affect failover or the circuit breaker: a provider that returns 403 counts as "reachable" in the connectivity check, yet it's unusable for real requests. Failover and the circuit breaker are driven only by the success or failure of real requests forwarded through local routing; see [4.3 Failover](./4.3-failover.md).

## FAQ

### The Check Shows Reachable, but Real Requests Fail

The connectivity check doesn't verify auth or models. Check:
- Whether the API Key is correct and matches the preset
- Whether the model name is supported by the provider
- Whether the upstream format matches the provider's API (see [2.1 Add Provider](../2-providers/2.1-add.md))

### Shows Unreachable

Possible causes:
- The request address is wrong
- The network is down, or access requires going through a proxy (configurable in "Settings → Routing → Global Outbound Proxy")
- A firewall is blocking the connection

### High Latency

Possible causes:
- Network latency
- High server load on the provider

Solutions:
- Use [Endpoint Speed Test](../2-providers/2.1-add.md#endpoint-speed-test) to pick a faster endpoint
- Adjust the slow-response threshold
