# XSEC Agent Shield：项目汇总与二次开发规划

> **文档版本：** 1.0\
> **整理日期：** 2026-10-19\
> **项目定位：** 面向 AI Agent 的本地优先安全防护与可逆数据脱敏平台\
> **建议仓库名：** `xsec-agent-shield`\
> **建议产品名：** XSEC Agent Shield

------------------------------------------------------------------------

## 1. 项目摘要

XSEC Agent Shield 计划基于开源项目 [CC
Switch](https://github.com/farion1231/cc-switch) 进行二次开发，构建面向
AI Agent 的安全防护产品。

核心能力是：在用户使用 AI Agent
时，尽可能在数据离开本机、发送给模型服务商之前，识别并替换敏感信息；在模型响应返回后，在本地将可恢复的占位符还原为原始信息。目标是减少个人开发者和企业在使用云端模型、编码
Agent 与多 Agent 工作流时的数据泄漏风险。

项目不应仅被理解为一个"脱敏插件"。中长期可以扩展为包含桌面客户端、本地安全运行时、模型
API 网关、Agent 适配器、策略管理和企业私有化部署能力的安全产品。

### 核心定位

**英文描述**

> XSEC Agent Shield --- Local-first security and reversible data
> redaction for AI agents.

**中文描述**

> 面向 AI Agent 的本地优先安全防护与可逆数据脱敏平台。

**设计原则**

-   本地优先：敏感数据映射与密钥尽可能留在用户设备或企业控制域内。
-   最小暴露：尽可能减少原始敏感信息发送给模型服务商。
-   可逆恢复：模型响应返回后，在本地安全恢复必要的原始值。
-   多入口防护：不依赖单一 MCP 协议，组合网关、Agent 适配器、Hook
    和本地运行时。
-   失败安全：严格策略下，无法确认已完成脱敏时不应静默回退为明文发送。
-   可验证：通过测试和指标衡量实际拦截能力，不以未经验证的百分比宣传安全效果。
-   可扩展：先交付最小可用版本，再逐步支持更多
    Agent、数据类型与企业策略。

## 5. 产品目标与威胁模型

### 5.1 主要目标

-   减少敏感信息进入第三方模型上下文。
-   让用户继续使用现有 AI Agent 和模型服务商。
-   尽可能保留 Agent 正常的编码、推理和工具调用体验。
-   将原始敏感值与替换令牌的映射保存在本地或企业受控环境中。
-   允许根据个人、项目、组织和数据类型配置策略。
-   对脱敏失败、代理故障和无法识别的内容提供明确的安全处理结果。

### 5.2 典型敏感信息

-   身份信息：姓名、手机号、邮箱、身份证件号等。
-   认证凭据：API Key、Token、密码、私钥、会话凭据。
-   企业数据：内部域名、服务器地址、数据库连接串、内部项目标识。
-   业务数据：客户信息、合同字段、订单信息和其他受策略约束的数据。
-   代码与配置中的秘密：`.env`、配置文件、日志、堆栈信息和源代码中的凭据。

检测规则应允许配置和调优。不是所有
IP、域名、代码片段或人名都必然属于敏感数据，应结合上下文、策略和误报成本判断。

### 5.3 需要明确的边界

"模型请求脱敏"并不等于"设备上所有数据都绝不会泄漏"。下列路径需要分别处理和验证：

-   Agent 发往模型服务商的请求。
-   工具调用参数和工具返回结果。
-   子 Agent 或其他模型客户端产生的请求。
-   文件读取、终端输出、日志和上下文拼接。
-   图片、音频、视频、PDF 和其他文件内容。
-   未经过本地代理的直连请求。
-   其他应用或进程发出的网络流量。
-   令牌映射、缓存、崩溃报告和本地日志本身。

本项目应公开说明各版本实际覆盖的路径，不应将有限的 API
拦截宣传为操作系统级的全面防泄漏。

## 6. 总体技术架构：方案 C

建议采用组合架构，而不是只做 MCP 服务。

``` text
用户
 │
 ▼
XSEC Agent Shield 桌面应用
 │
 ├── Agent 配置与适配器
 │    ├── Agent Hook / 插件
 │    ├── 请求入口适配
 │    └── 工具与子 Agent 适配（按 Agent 能力实现）
 │
 ├── 本地安全运行时
 │    ├── 策略引擎
 │    ├── 敏感信息检测
 │    ├── 可逆令牌管理
 │    ├── 本地加密存储
 │    └── 安全事件记录
 │
 ├── 本地 API 代理 / 请求中间件
 │    ├── 请求解析
 │    ├── 脱敏
 │    ├── 上游模型请求
 │    ├── 流式响应处理
 │    └── 响应恢复
 │
 └── MCP 服务（辅助能力入口）
      └── 供支持 MCP 的 Agent 调用策略查询或受控工具
```

### 6.1 为什么不能只使用 MCP

MCP 是 Agent 与工具之间的协议，不是天然的全局模型请求拦截器。仅实现 MCP
Server，无法保证所有发往模型服务商的系统提示、用户消息、历史上下文、工具结果和子
Agent 请求都会经过它。

因此，MCP 可以作为辅助集成方式，但不能独自承担完整的数据出口保护责任。

### 6.2 API 网关的职责和局限

API
网关或本地代理可以统一处理经过它的模型请求与响应，适合承载脱敏、恢复、策略检查和审计。但它无法自动覆盖绕过代理的直连请求，也不能天然拦截
Agent 在本地执行的所有文件和工具操作。

### 6.3 Agent Hook / 插件的职责和局限

Hook 或插件可在特定 Agent
生命周期节点介入，例如请求提交前、工具调用前后或会话事件处理。但各 Agent
的扩展机制不同，能力、执行时机和可见数据范围都需要分别验证。不能假设一个
Hook 能覆盖所有 Agent。

### 6.4 推荐原则

**一个统一脱敏内核，多个受控入口。**

-   桌面应用负责配置、状态展示和用户交互。
-   本地运行时负责策略、密钥和敏感信息映射。
-   API 代理负责其可覆盖范围内的请求/响应处理。
-   Agent 适配器负责特定 Agent 的生命周期接入。
-   MCP 提供可选的工具协议集成，不承担唯一的强制安全边界。

## 7. 可逆脱敏核心设计

### 7.1 基本处理流程

1.  接收待发送的请求内容。
2.  根据内容类型解析文本、结构化数据和可处理的多模态输入。
3.  执行敏感信息检测和策略判定。
4.  为需要替换的敏感值生成会话级或作用域级令牌。
5.  将原始值与令牌映射以受保护方式保存在本地。
6.  把脱敏后的请求交给上游模型服务。
7.  接收模型返回的响应或流式数据。
8.  识别属于本次授权映射范围的令牌，并按策略恢复原始值。
9.  将恢复后的内容交回 Agent。
10. 按策略记录最小化的安全事件，不默认记录完整原始请求正文。

示例：

``` text
原始输入：
请检查连接数据库的配置，密码是 S3cr3t-Example。

发往模型的内容：
请检查连接数据库的配置，密码是 <SECRET_01>。

模型响应：
建议轮换密码 <SECRET_01> 并检查配置文件权限。

本地恢复后的响应：
建议轮换密码 S3cr3t-Example 并检查配置文件权限。
```

示例仅用于解释机制。实际令牌应避免与用户输入或模型生成内容冲突，并应绑定会话、请求或其他安全作用域。

### 7.2 关键安全要求

-   使用密码学安全的随机数生成器生成不可预测令牌。
-   映射数据加密存储；密钥管理与数据存储分离设计。
-   不将原始敏感值直接放入日志、崩溃报告或遥测数据。
-   令牌应有作用域、过期策略和清理机制。
-   防止跨用户、跨租户、跨会话或跨请求误恢复。
-   恢复前校验令牌是否属于当前会话和授权范围。
-   防止模型自行编造相似令牌导致错误恢复。
-   对重复值、嵌套结构、转义字符、Unicode 和截断内容进行测试。
-   对流式输出定义明确的缓冲、边界检测和超时策略。
-   对失败情况提供可解释的错误与审计事件。

### 7.3 令牌恢复的风险

可逆脱敏并不意味着可以盲目全局替换。若模型输出了猜测或伪造的令牌，或同一令牌在不同会话复用，可能造成错误恢复或信息串扰。

建议至少做到：

-   令牌使用足够高的随机性或不可猜测性。
-   令牌与会话、请求及数据类型建立作用域关联。
-   仅恢复当前上下文中确实存在且授权的映射。
-   对未知令牌保持原样或按策略拒绝，不能猜测原值。
-   为跨请求引用和工具调用明确令牌生命周期。

## 8. 流式响应与多模态处理

### 8.1 流式响应

模型可能逐块返回文本，令牌也可能被分割在不同的数据块中。因此不能只对每个
chunk 独立执行字符串替换。

需要设计：

-   有界缓冲区和跨 chunk 匹配。
-   最大缓冲长度与超时控制。
-   令牌完整性检查。
-   兼顾首字延迟、吞吐量与恢复正确性的策略。
-   流中断、取消、重试和部分响应的处理。
-   严格模式下，无法安全处理的输出如何中止或隔离。

### 8.2 多模态内容

图片、音频、视频和文件不能仅靠文本正则表达式完成全面脱敏。不同数据类型需要不同的提取和策略：

-   文档：解析文本层、元数据和可访问的嵌入内容。
-   图片：OCR、元数据清理及必要时的图像区域处理。
-   音频：语音识别文本、元数据及适用的音频处理策略。
-   视频：关键帧、字幕、音轨和元数据。
-   代码仓库：扫描源码、配置、提交差异和常见秘密格式。

首期应限制支持范围并清晰声明。若暂时无法可靠检测某种内容，严格模式下应阻断或要求用户确认，而不是假装已完成全面脱敏。

## 9. 安全失败策略

建议提供至少两种模式：

### 9.1 严格模式（Fail-Closed）

当本地代理不可用、解析失败、检测器异常、策略无法加载或脱敏结果无法确认时，阻止请求继续发送，并向用户说明原因。

适用于高敏感度企业环境、受监管数据和明确要求不允许明文外发的场景。

### 9.2 兼容模式

允许用户在明确配置和提示下，对特定错误采取有限降级。但必须显示风险、记录安全事件，并避免静默回退到明文发送。

不建议把自动明文回退设为默认行为。

### 9.3 必须测试的故障场景

-   本地代理进程被终止。
-   网络断开或上游请求超时。
-   检测引擎崩溃。
-   映射存储不可读或数据库损坏。
-   密钥丢失或权限错误。
-   流式响应中断。
-   模型返回伪造或截断令牌。
-   Agent 绕过代理直连服务商。
-   子进程或子 Agent 使用独立网络路径。
-   应用升级、重启和异常退出。

## 10. 技术实施路线

### 阶段 0：仓库基线与合规

-   固定上游 fork 的 commit。
-   检查根目录 LICENSE、依赖许可证和第三方资源。
-   记录当前 CC Switch 功能与代码边界。
-   设定新的应用名、图标、包标识和发布渠道。
-   建立安全需求、威胁模型与测试清单。
-   在分支中保留可回滚的最小修改。

### 阶段 1：最小可行原型（MVP）

目标是先证明可逆脱敏链路在本地代理场景中可行，而不是一开始支持所有 Agent
和多模态。

实现：

1.  本地请求代理或现有路由链路接入。
2.  请求发送前的文本敏感信息检测。
3.  可逆令牌生成与映射存储。
4.  本地加密映射存储的基础实现。
5.  响应恢复。
6.  基础流式响应处理。
7.  严格模式和代理失效阻断。
8.  最小化日志，不记录完整原始正文。
9.  针对 Claude Code、Codex 等目标 Agent
    做真实链路验证，具体以其当前可配置的请求路径为准。

MVP 验收至少覆盖：

-   普通请求能脱敏并正确恢复。
-   响应中多个令牌的恢复顺序正确。
-   流式 chunk 拆分令牌时仍能正确处理。
-   未知令牌不会被错误恢复。
-   代理失效时严格模式不会静默明文直连。
-   本地映射数据不以明文写入磁盘或日志。
-   测试可重复执行并有明确结果。

### 阶段 2：Agent 适配器与工具链路

-   为每个目标 Agent 独立分析请求、Hook、配置和子进程机制。
-   建立适配器接口，避免把 Agent 特定逻辑耦合进核心内核。
-   验证工具调用参数、工具结果和上下文拼接是否经过受控路径。
-   检查子 Agent、后台任务和重试路径。
-   提供状态诊断：哪些路径已保护、哪些路径未覆盖、哪些请求绕过保护。

### 阶段 3：策略与可观测性

-   自定义敏感信息规则。
-   按项目、会话、模型和数据类型配置策略。
-   用户可审查的事件记录。
-   令牌过期与清理。
-   误报/漏报反馈机制。
-   性能指标与故障统计。
-   安全策略导入导出。

### 阶段 4：多模态与企业能力

-   文档、图片和其他多模态内容的渐进式支持。
-   企业策略模板与集中管理。
-   私有化部署。
-   企业密钥管理与访问控制。
-   可选的审计与合规报告。
-   与组织身份、终端管理和安全运营体系集成。

## 11. 验证指标与测试策略

不应在缺乏实验数据时宣称"99%
拦截率"或"零泄漏"。需要定义测试数据集、威胁边界和指标口径。

建议至少跟踪：

  指标             含义
  ---------------- ----------------------------------------------------
  敏感信息召回率   已标注敏感项中被正确识别的比例
  检测精确率       被系统判定为敏感的项中实际正确的比例
  脱敏成功率       应脱敏项中成功替换且满足规则的比例
  恢复正确率       应恢复的令牌中被正确恢复的比例
  错误恢复率       不应恢复的内容被错误恢复的比例
  旁路泄漏率       在定义的旁路测试中，敏感数据未经保护进入上游的比例
  故障阻断率       严格模式下，故障场景中成功阻止未受保护请求的比例
  性能开销         代理增加的延迟、CPU、内存和吞吐量变化
  兼容性           不同 Agent、模型、工具和响应模式的测试通过情况

### 必测测试类别

-   单条敏感信息、多个敏感信息、重复值和嵌套文本。
-   中文、英文、Unicode、转义字符和混合格式。
-   JSON、代码块、日志、堆栈和长文本。
-   流式 chunk 边界、截断、重试与取消。
-   工具调用、工具返回、子 Agent 和后台任务。
-   本地代理失效、密钥不可用和存储异常。
-   多会话并发、跨租户隔离和映射过期。
-   图片、文档等已声明支持的输入类型。
-   直接连接模型服务商的旁路测试。

旁路测试应成为产品安全报告的重要组成部分。任何未被拦截的路径都应记录为覆盖缺口，而不是通过统计口径掩盖。

## 12. 产品界面与用户体验建议

桌面端可以延续 CC Switch
的成熟交互基础，但产品信息架构应围绕"安全状态"而非单纯模型配置组织。

建议主导航：

1.  **总览**：当前保护状态、活动会话、策略状态、风险提示。
2.  **Agent 管理**：已识别 Agent、适配器状态、覆盖范围。
3.  **脱敏策略**：规则、数据类别、例外和严格模式。
4.  **令牌与会话**：仅展示必要的脱敏元数据；原始值应受严格权限控制。
5.  **安全事件**：脱敏成功、阻断、异常和旁路风险。
6.  **模型与代理**：模型服务商、本地代理与连接诊断。
7.  **设置**：密钥管理、数据保留、日志、更新和隐私控制。

重要 UX 要求：

-   明确展示当前是否处于受保护状态。
-   显示每个 Agent 的覆盖范围和未覆盖路径。
-   对需要用户决策的明文发送行为提供明确警告。
-   不以"已开启保护"暗示所有数据出口都已被拦截。
-   避免在 UI、日志、错误报告和崩溃报告中暴露原始敏感值。

## 17. 结论

建议将 `xsec-agent-shield` 作为独立产品仓库名，以 CC Switch
作为桌面与配置管理基础，把差异化投入放在安全内核、可逆脱敏、响应恢复、Agent
数据路径覆盖、失败安全和可验证的测试体系上。

项目成败的关键并非是否接入
MCP，而是能否明确并控制真实的数据出口：哪些请求经过脱敏、哪些路径可能绕过、异常时是否会明文放行，以及敏感映射能否在本地得到可靠保护。

先完成一个范围清晰、可以验证的本地 MVP，再逐步扩展到更多
Agent、工具链路、多模态数据和企业私有化部署。商业化前应完成许可证、依赖和商标审查，并以独立品牌发布。
