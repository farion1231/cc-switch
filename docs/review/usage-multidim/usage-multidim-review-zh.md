## 3. 发现与处理

### R-01 直连模式无法从现有日志得到真实供应商

严重程度：高

问题：Codex 第三方供应商共用 `model_provider = "custom"`，会话日志没有保存具体供应商。其他客户端也存在占位供应商或原生供应商字段未导入的问题。仅根据当前选中的供应商或模型价格推断，会把历史请求归到错误供应商。

处理：需求增加供应商激活时间线，按请求时间点查找唯一有效的直连供应商；没有证据时进入未识别桶。对应需求 FR-01、FR-02 和 10.1。

结论：已解决。

### R-02 去重后可能丢失会话日志上的项目

严重程度：高

问题：现有去重逻辑在代理行与会话行重复时保留代理行。代理行只有 session_id，没有项目字段；如果丢掉会话行，会把会话行上的项目证据一起丢掉。

处理：需求要求去重后的有效行同时保留代理供应商和会话项目，允许查询时通过会话项目索引补全。对应 FR-04 和 10.2。

结论：已解决，实现时必须用集成测试锁住；精确的去重机制（write-side skip + read-side filter）见 R-22。

### R-03 日汇总主键没有项目维度

严重程度：高

问题：当前 `usage_daily_rollups` 主键不包含项目。只给明细增加项目，30 天后明细裁剪，项目维度会消失。

处理：需求要求重建日汇总表，把 `project_key` 纳入主键，并明确旧数据回填为空。对应 9.4、9.5。

结论：已解决。

### R-04 供应商统计没有缓存分母

严重程度：高

问题：现有 `ProviderStats` 只返回总 Token 和成本，没有新增输入、缓存写入、缓存命中的分组结果。只返回一个百分比无法校验加权关系，也无法区分“命中率 0%”和“没有可缓存输入”。

处理：需求要求供应商、项目、模型统计同时返回三类 Token、可缓存输入和命中率；UI 在分母为 0 时显示 `—`。对应 FR-05 和 11。

结论：已解决。

### R-05 路由模式 session_id 不一定能关联项目

严重程度：高

问题：代理侧可能生成 session_id，未必等于客户端会话 ID。代码注释已经明确代理行的会话 ID 是代理侧推断的，未必对得上。

处理：需求要求按客户端适配器规范化 session_key、优先关联、无法关联时项目未识别；供应商仍以代理日志为准。对应 FR-04、13.2、20。

结论：已接受为产品边界，不能承诺路由模式项目 100% 识别。

### R-06 旧版本无法打开新 schema

严重程度：高

问题：数据库 `user_version` 高于应用支持版本时，当前代码会拒绝启动。升级到 v21 后直接降级旧版本不可行。

处理：需求明确回滚必须使用迁移前自动备份恢复，不把旧版本直接打开新库作为回滚方案。对应 9.5、16.3。

结论：已解决，发布说明必须写明。

### R-07 同一上游多张卡片会分成多行

严重程度：中

问题：用户可能为同一供应商配置多个 Key 或多个套餐。按卡片统计更精确，但列表行数会变多。

处理：P0 明确按供应商卡片统计，不按 base_url 合并；P2 再提供品牌维度。对应 5.1、19。

结论：已接受。

### R-08 官方订阅成本不是实际账单

严重程度：中

问题：ChatGPT 订阅按 API 等价价格展示时，金额是估算值，不是用户实际支付给供应商的账单。

处理：需求要求 UI 标注“估算”，不得称为实际账单；改为 0 成本必须单独决策。对应 FR-06。

结论：已解决。

### R-09 项目路径归一化可能造成重复或错误合并

严重程度：中

问题：符号链接、尾斜杠、Windows 分隔符、路径不存在都会影响项目键稳定性。

处理：需求定义路径规范化顺序和回退规则，并要求单元测试覆盖。对应 FR-03、16.1。

结论：已解决，需在 macOS 和 Windows 上验证。

### R-10 历史数据无法完整回填

严重程度：中

问题：已裁剪明细没有 session_id，功能上线前没有供应商激活历史，无法可靠还原项目或供应商。

处理：需求明确历史数据保持未识别，不根据当前状态反推；只回填仍保留的明细和仍可解析的会话。对应 13。

结论：已接受。

### R-11 外部修改 live 配置会使时间线失真

严重程度：中

问题：用户或其他工具直接修改客户端 live 配置后，供应商激活时间线可能与实际配置不一致。

处理：需求要求保存配置指纹；匹配失败时进入未识别，不使用当前激活记录兜底。对应 FR-01、FR-02、20。

结论：已解决。

### R-12 项目路径属于本机敏感信息

严重程度：中

问题：完整路径可能包含用户名、内部项目名或目录结构。进入遥测或导出会带来隐私风险。

处理：需求限定路径只在本地展示，不进入遥测；导出默认不包含完整路径。对应 15。

结论：已解决。

### R-13 缓存命中率 0% 与不可计算混淆

严重程度：低

问题：如果只返回浮点数，无法区分“有可缓存输入但零命中”和“没有可缓存输入”。

处理：需求要求同时返回可缓存输入 Token，UI 根据分母决定显示 `0%` 还是 `—`。对应 FR-05。

结论：已解决。

### R-14 不同客户端的项目与供应商证据不一致

严重程度：高

问题：Claude、Codex、Gemini、Grok Build 主要通过切换时间线归属供应商；OpenCode、Pi、MiniMax Code 已有不同程度的原生供应商线索；Claude Desktop、OpenClaw、Hermes、Cursor 的用量或项目来源不完整。用一套字符串规则套所有客户端会误归因。

处理：需求增加客户端能力矩阵和 FR-11 适配器契约，要求每个客户端声明用量来源、项目来源和供应商策略。切换式客户端使用时间线，累加式客户端优先使用原生供应商字段，缺能力时进入未识别。对应 2.1、FR-01、FR-02、FR-11。

结论：已解决，代码实现时必须用能力矩阵和注册表测试防漂移。

### R-15 Cursor 当前不能直接产生统计

严重程度：中

问题：当前 `AppType` 没有 Cursor，也没有 Cursor 会话用量适配器。只增加项目页签或在常用客户端列表里展示 Cursor，会制造无数据来源的产品假象。

处理：需求明确 Cursor 属于后续接入项，必须先完成客户端注册、配置写入、用量来源、项目识别和供应商映射，才能进入统一统计。对应 2.1、4.2、18、20。

结论：已接受为当前版本边界，不影响已有客户端接入统一模型。

### R-16 迁移前无法恢复供应商名称快照

严重程度：中

问题：现有明细和日汇总没有供应商名称快照。迁移前已经删除或改名的供应商，无法证明历史显示名称。

处理：需求要求新写入行在请求发生时保存名称快照；迁移时只从现存的 `providers` 表尽力回填，无法恢复时显示未识别名称，不伪造历史。对应 FR-10、9.3、9.5、13.2。

结论：已接受为历史数据边界。

### R-17 日汇总只存项目键会让项目路径丢失

严重程度：高

问题：如果 `usage_daily_rollups` 只保存 `project_key` 和 `project_name`，明细裁剪后无法稳定展示项目完整路径；会话项目索引也可能被清理。

处理：日汇总增加 `project_path` 快照，和名称一起在汇总时写入。项目路径仍只在本地展示，不进入遥测。对应 9.4、13、16。

结论：已解决，迁移和日汇总测试必须覆盖路径保留。

### R-18 供应商名称快照只写入但没有读侧优先级

严重程度：高

问题：数据模型增加 `provider_name_snapshot`，但需求只写了写入和迁移回填，没有规定查询展示时优先使用快照。实现如果继续实时 `LEFT JOIN providers.name`，供应商改名后历史名称仍会被覆盖，删除后仍显示空值。

处理：FR-10 和 11.3 明确读侧优先使用 `provider_name_snapshot`，只有快照为空时才回退实时名称。对应 FR-10、9.3、11.3。

结论：已解决。

### R-19 新客户端的输入 Token 语义没有纳入能力声明

严重程度：高

问题：缓存命中率依赖 `fresh_input_sql` 对 OpenAI 式 `input_tokens` 的归一化，`CACHE_INCLUSIVE_APP_TYPES` 在 Rust 和前端分别维护。新增客户端如果未声明输入语义，缓存写入和缓存命中会被重复计数，命中率分母错误。

处理：FR-11 增加 `inputTokenSemantics: fresh | total`，并要求同步 Rust 和前端常量。对应 FR-11。

结论：已解决，新增客户端测试必须覆盖 fresh/total 两类口径。

### R-20 人工覆盖表缺少时间范围字段

严重程度：中

问题：需求说明人工覆盖支持时间范围，但 `usage_attribution_overrides` 只有 `scope_key`，没有范围起止字段，无法表达区间覆盖。

处理：为表增加 `scope_start_at`、`scope_end_at`，并明确 `time_range` 用起止字段定位。对应 9.6。

结论：已解决。

### R-21 API 章节的接口名与实现不符

严重程度：中

问题：需求写了 `get_daily_stats`，但实际 Tauri 命令是 `get_usage_trends`（返回 `DailyStats`）；`get_session_usage_summary` 只接受应用和会话 ID，不应套用项目筛选。

处理：12.1 改为真实接口名，并补充 `get_usage_first_date` 的项目筛选和单会话查询的例外。对应 12.1、FR-07。

结论：已解决。

### R-22 去重描述把 write-side skip 当成了 read-side 隐藏

严重程度：高

问题：需求原文把跨源去重描述为“隐藏会话行、保留代理行”，并认为读取时可以从被隐藏的会话行继承项目。实际代码是两条路径并存：写入会话行前 `should_skip_session_insert`（`src-tauri/src/services/usage_stats.rs:693`）先按指纹命中代理行并跳过插入（write-side skip），调用点在 `session_usage.rs:1188`、`session_usage.rs:1272`、`session_usage_codex.rs:2194`、`session_usage_gemini.rs:275`、`session_usage_opencode.rs:460`；已落库的历史会话行才由 `effective_usage_log_filter` 读侧 `NOT EXISTS` 过滤。新会话行在被跳过前若没有把项目证据写回代理行或关联记录，项目证据会彻底丢失，读取时无会话行可继承。

处理：FR-04、10.2、7 的设计原则和验收项已改为“去重判定时先回写项目证据”，并把 `session_usage.rs`、`session_usage_codex.rs`、`session_usage_gemini.rs`、`session_usage_opencode.rs` 的跳过调用点列为改造对象。对应 FR-04、10.2、21。

结论：已解决，集成测试必须覆盖“会话行被跳过前项目已回写”的写入侧断言，而不能只验证读侧过滤结果。

## 4. 一致性检查

### 4.1 总量守恒

检查了以下关系：

- 各应用行之和等于应用总计。
- 各供应商行之和等于供应商总计。
- 各项目行之和等于项目总计。
- 项目 × 应用行之和等于对应项目。
- 项目 × 供应商行之和等于对应项目。
- 模型行之和等于当前筛选范围总计。
- 去重前后请求数、Token、成本不变。

需求在 FR-02、FR-04、FR-05、FR-07 和验收表 A04、A05、A06 中做了对应约束。

结论：通过。

### 4.2 缓存口径一致

检查了整体、项目、供应商、模型四个层级是否使用同一公式和同一批去重行。

需求在 11.3 明确要求不能各自走不同去重逻辑，不能用百分比算术平均。

结论：通过。

### 4.3 直连与路由边界

检查了以下场景：

- 直连切换供应商。
- 直连切路由。
- 路由切直连。
- 路由请求与会话日志重复。
- 代理 session_id 无法关联项目。

需求分别使用供应商时间线、代理日志和未识别桶处理，没有把两类证据混为一条规则。

结论：通过。

### 4.4 迁移与回滚

检查了旧数据库、明细行、汇总行、旧版本和新版本：

- 新表可以新增。
- 明细列可以用默认值补齐。
- 汇总表需要重建主键。
- 旧数据项目为空，显示未识别。
- 旧版本不能直接打开新库，回滚依赖备份。

需求在 9.5、13、16.3 中完整描述。

结论：通过，但迁移测试是发布门禁。

### 4.5 API 与 UI 对应

检查了应用和项目筛选是否作用于所有视图，新增接口是否都有对应 UI 数据来源，未接入用量的客户端是否会被错误展示为 0 用量。

结论：通过。

### 4.6 多客户端适配边界

检查了 `AppType` 当前注册项、会话管理器和会话用量同步器的对应关系：

- Claude Code、Codex、Gemini CLI、OpenCode、Grok Build、Pi、MiniMax Code 已有会话用量同步器。
- Claude Desktop 当前只有代理用量路径。
- OpenClaw、Hermes 有会话和项目目录能力，但没有会话用量同步器。
- Cursor 尚未注册，也没有用量来源。

需求已将上述差异写入客户端能力矩阵，并通过 FR-11 区分 `session`、`proxy`、`both`、`none`，没有假设所有客户端已经具备相同数据。

结论：通过。

### 4.7 应用与供应商身份隔离

检查了数据库现有的 `(id, app_type)` 供应商身份、统计查询的 `(provider_id, app_type)` 分组、Claude Desktop 展示折叠规则，以及项目默认跨客户端合并的语义。

- 同一项目被多个客户端使用时，项目行默认合并。
- 供应商行按应用隔离，避免同名供应商 ID 串数据。
- `claude-desktop` 只在展示和筛选口径折叠进 `claude`，底层关联仍保留原始 `app_type`。
- `appType` 筛选可以恢复单客户端视图。

结论：通过。

## 5. 剩余风险

| 编号 | 风险 | 影响 | 验证方式 |
| --- | --- | --- | --- |
| 1 | 代理 session_id 由代理侧生成 | 路由模式项目未知 | 构造无法关联的 session_id 集成测试 |

| 3 | 用户直接修改 live 配置 | 时间线失真 | 配置指纹不匹配测试 |

| 6 | 旧汇总数据无法拆项目 | 历史项目视图不完整 | 迁移后核对未识别比例 |
| 7 | 项目路径跨平台差异 | 同项目被拆成多个键 | macOS 与 Windows 路径测试 |
| 8 | 新增客户端只接 UI 未接数据源 | 出现空页签或伪造用量 | 能力矩阵、注册表和空数据测试 |
| 9 | 相同供应商字符串跨应用冲突 | 供应商统计串数据 | 使用 `(app_type, provider_id)` 组合键测试 |
| 10 | 迁移前供应商已删除或改名 | 历史名称无法恢复 | 检查名称快照回填结果和未识别展示 |
| 11 | 日汇总缺少项目路径快照 | 明细裁剪后路径丢失 | 迁移与日汇总后路径保留测试 |
| 12 | 快照列未用于读侧展示 | 供应商改名删除后历史名称错误 | 名称快照优先读取测试 |
| 13 | 新客户端输入 Token 语义未声明 | 缓存命中率分母错误 | fresh/total 归一化对照测试 |
| 14 | 人工覆盖表缺少时间范围字段 | 无法表达区间覆盖 | 覆盖表 schema 和范围匹配测试 |
| 15 | API 名称和参数与实现不一致 | 前后端联调失败 | 命令签名对照测试 |
| 16 | 去重按 write-side skip 跳过会话行 | 会话项目证据在写入前丢失 | 写入侧回写项目断言 + 读侧过滤结果核对 |

## 6. 评审结论

需求已覆盖以下闭环：

1. 所有客户端共享应用、供应商、项目、模型、时间维度，供应商归属按客户端能力选择证据来源，不依赖当前状态反推。
2. 项目归属有会话 cwd 来源，代理日志有 session 映射和未知回退。
3. 缓存命中率在整体、项目、供应商、模型四层保持同一公式和加权口径。
4. 明细和日汇总都保留项目维度。
5. 去重路径明确保留项目和供应商证据。
6. 历史数据、外部修改、代理 session_id 不可关联等场景都有未识别处理。
7. 已有用量来源的客户端进入 P0，Cursor 和不完整客户端通过能力声明与适配器逐步接入。
8. 迁移、回滚、性能、安全和测试均有明确验收项。

未发现阻塞性问题。评审结论为“可进入实现拆解”，但以下六项必须作为发布门禁：

1. v20 到 v21 迁移与备份恢复测试必须通过。
2. 路由模式代理行与会话行去重后项目不丢失的集成测试必须通过，且必须覆盖 write-side skip（会话行在写入前被跳过）时项目证据已回写代理行或关联记录。
3. 供应商、项目、整体三层缓存命中率加权一致性测试必须通过。
4. 无法归属的数据必须实际进入未识别桶，不能静默回退到当前供应商或当前项目。
5. 客户端能力矩阵、`AppType` 注册表和用量适配器注册表必须一致。
6. 相同供应商 ID 出现在不同 `app_type` 时，统计结果必须保持隔离。
7. 供应商名称快照的读侧优先级必须与需求一致，改名删除后历史名称不漂移。
8. 新增客户端的输入 Token 语义必须与 Rust、前端两处 `CACHE_INCLUSIVE_APP_TYPES` 一致。
